# 食材字典 · 预制成品

> 覆盖范围:速冻面点 · 速冻荤菜 · 速冻炸物 · 熟食卤味 · 醉糟生食 · 半成品馅料 · 酱料汤底 · 即食成品 · 西式成品。
> 来源:`../recipes/01~06` 六个文件 `## prepLevel 变体` 表里 `readymade` / `assembled` 两档引用、而现有三个字典查不到的**成品**。
> ⚠️ **全表未验证。** 包装规格 · 计件单位 · 成本档 · 参考价全部是六路 agent 的未核实估计,`可信度` 列一律 `B` 或 `C`,拿不准的留 `—`,**没有编造**。
> ⚠️ **`保质期` 列六路 agent 一条都没给**,除少数原报告写明「开封后如何处理」的以外一律留空。速冻面米制品的国标印制保质期通例是 −18℃ 12 个月,但那是通例不是本表的数据,没有逐条写进去。
> ⚠️ **`单位换算` 列同样是估计值,可信度 C,须人工校准。** `计件单位` 说的是「按只/张/个卖」,但求解器要的是**一只多少克**,不然对不上 `包装规格` 里的总重。本列绝大多数是从 `包装规格` 现成反推的(`500g/袋(约 20-30 只)` → `1只≈20g`),没有另编;包装只给件数不给克重的才凭常识估,估的都在括号里标了区间。只给菜谱里确实按件写过的条目填,其余留 `—`。

## 为什么成品要单独一个文件

现有三个字典只收「原子食材」,`01-动物性.md` 的「已知未收录」表明确把速冻饺子判为「**复合成品,不是单一食材**」而拒收。但 `SPEC.md` 的 `prepLevel` 一节要求 `readymade` / `assembled` 档**必须引用成品 id**(它自己举的例子就是 `frozen_har_gow`)。两边只能选一头。

**裁决**:字典的职责不是「原子食材」,是**「你会买的东西」**。整个项目是食材流转 / 采购管理器,粒度应该对齐 **SKU** 而不是对齐分类学。没有 id 的成品 → 进不了采购清单 → 没有包装规格 → 没有保质期 → 没有成本档 → **那一档对求解器就是不可解的**。

但成品确实是另一类东西,所以另开本文件而不是塞进现有三个:

| 差异 | 原子食材(01/02/03) | 成品(本文件) |
|---|---|---|
| 计量 | 按 100g 给营养,按克买 | **常按件买**(8 只 / 1 张 / 1 袋),件数直接决定「一个人四顿吃不吃得完」 |
| 营养 | 单一食材的可食部估计值 | 复合的,随品牌配料表变,没有可信的单一数值 —— 故本表**不设营养列** |
| 过敏原 | 通常 0-1 个 | 通常 2-4 个(速冻虾饺 = 虾 + 小麦) |
| 「牺牲了什么」 | 不存在这个维度 | **是选档的全部依据**,故单列一列 |
| 对应关系 | 与菜谱是多对多 | **是某几道菜的某一档专用**,故单列 `对应菜谱ID` |

### 与另外三个字典的分工

| 文件 | 收什么 | 边界例子 |
|---|---|---|
| `01-动物性.md` | 生鲜肉蛋水产乳 + **加工肉**(腊肠/培根/叉烧/卤牛肉) | `char_siu` 叉烧、`braised_beef` 卤牛肉、`beef_tripe` 熟卤牛肚**已在 01**,本表不重复建 |
| `02-蔬菜菌菇水果.md` | 生鲜蔬果菌菇鲜香料 + **腌渍菜** | `kimchi` 泡菜、`pickled_chili` 泡椒在 02,不在本表 |
| `03-主食干货调料.md` | 米面杂粮 · 豆制品 · 干货 · 调料 · 香料 · **面点皮和现成面条** | `dumpling_wrapper` 饺子皮、`fresh_wheat_noodle` 鲜面条、`puff_pastry` 酥皮、`pie_crust` 派皮在 03 —— 它们是**半成品原料**,不是成品菜 |
| **`04-预制成品.md`(本文件)** | **已经是一道菜或一份点心、买回来只需加热/摆盘的东西** | 速冻虾饺 · 真空红烧肉 · 冷冻披萨 · 酸菜鱼调料包 |

**分界线**:`dumpling_wrapper`(饺子皮)是 03,`frozen_dumpling`(速冻水饺)是 04。前者你还得自己包,后者下锅就行。

### 可信度口径(沿用 `../packages.md`)

| 标记 | 含义 |
|---|---|
| **B** | 两路 agent 独立给出同一规格,互相印证 —— 全表只有 2 条 |
| **C** | 单路 agent 按零售常识推测,**无商品页出处,必须人工校准** —— 其余 48 条 |

没有一条是 A。参考价只有 02 和 05 两路给了,其余留空。

### 含酒口径(与 `01` / `02` / `03` 同名列对齐)

取值只有 `是` / `否`,四个字典一致,列位一律在「过敏原」之后。`03` 把「配料含酒源」一律判 `是`,**不看成品里还剩多少酒精**;本表沿用这个偏保守的方向。

📌 **本轮更正一处误读**:上一版这里写着「`03` 的 `white_wine_vinegar` 判 `是`,备注却写成品几乎不含酒精」。那是**看串列了** —— 该行的 `是` 在「必然过量」列(倒数第 2 列),不在「含酒」列(第 7 列)。`03` 的八条醋**从来就全是 `否`**,并不存在自相矛盾,详见 `03` 醋类一节末尾的裁决。

⚠️ **本表与 `01` / `02` 的判据不是同一条**(取值和列位相同,推法不同,这是刻意的):`01` / `02` 是原子食材,用的是「买回来直接吃 / 直接用会不会摄入酒精」,即**成型阶段有没有经历足以挥发酒精的加热**;本表是复合成品,配料表读不到,只能靠菜谱数据反推,规则见下。

成品不是原子食材,配料表读不到,所以逐条的判据取自**本库自己的菜谱数据**,规则一条:

> **主表那道菜的 `调料` 列含酒源,而它的 `readymade` / `assembled` 变体行不再单列这个酒源 → 酒被吸收进成品 → 本表判 `是`。**
> 变体行仍然单列着酒(用户自己另买)→ 判 `否`,酒精由那味调料自己的 `含酒` 字段负责。

这条规则直接来自 `DESIGN.md` 的「含酒精 = 各食材 `hasAlcohol` 的或」。**不这么判,同一道菜切到 `readymade` 档时含酒标记会静默翻成「否」** —— 那才是这一列要修的 bug。

两条判 `否` 的例子,正是靠变体行救回来的:

| id | 主表酒源 | 变体行 | 判定 |
|---|---|---|---|
| `frozen_tempura` | RH-004 / RH-023 的 `味淋[mirin]` | 变体行**仍列 `味淋`**(天丼汁自己调) | `否` |
| `frozen_lion_head` | YZ-045 / BF-029 的 `料酒[cooking_wine]` | BF-029 变体行**仍列 `料酒`**(买生冻丸子回来自己烧) | `否` |

⚠️ 与全表其余列一样,这一列是**推的不是读的**,可信度等同 `C`,须人工校准。备注里原有的 `⚠️ 含酒未加热` 保留 —— 字段只答「含不含」,答不了「酒精挥发没有」。

### B. `lemon` 的「柠檬汁」:判为别名,菜谱**不用改**
